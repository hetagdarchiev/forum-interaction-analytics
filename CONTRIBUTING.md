# Разработка Comunicore

> **Главная схема:** `main → новая ветка → изменения → проверки → Pull Request → merge`

* Прямые push в `main` запрещены. Один Pull Request должен решать одну задачу.
* Перед началом всегда подгружайте изменения из main `git pull origin main`.

## 1. Быстрый ориентир

| Что | Главное правило |
| --- | --- |
| Начало работы | обновить `main` и создать новую ветку |
| Ветка | `тип/название-задачи` |
| API | сначала OpenAPI, затем кодогенерация |
| База данных | новая миграция + `sqlc generate` |
| Pull Request | одна задача, проверки пройдены |
| Слияние | по умолчанию `Squash and merge` |

### Пример

```text
Задача:  обновить README
Ветка:   refactor/update-readme
Merge:   Squash and merge
```

Названия коммитов не регламентируются.

## 2. Рабочий процесс

### Шаг 1. Обновить `main`

```bash
git switch main
git pull --ff-only origin main
```

### Шаг 2. Создать ветку

```bash
git switch -c тип/название-задачи
```

Пример:

```bash
git switch -c feat/thread-subscriptions
```

### Шаг 3. Зафиксировать изменения

```bash
git status
git diff
git add <изменённые-файлы>
git commit -m "описание изменений"
```

### Шаг 4. Отправить ветку

```bash
git push -u origin тип/название-задачи
```

После первой отправки достаточно команды `git push`.

### Шаг 5. Создать Pull Request

Создайте PR в `main`, заполните описание и дождитесь прохождения CI.

## 3. Именование веток

Формат:

```text
тип/название-задачи
```

Правила:

- латиница и нижний регистр;
- слова разделяются дефисами;
- одна ветка — одна задача;
- название должно кратко описывать изменение.

Примеры:

```text
feat/thread-subscriptions
fix/session-expiration
docs/update-readme
refactor/auth-service
```

### Типы веток

| Тип | Когда использовать |
| --- | --- |
| `feat/` | новая функция |
| `fix/` | исправление ошибки |
| `docs/` | документация |
| `refactor/` | изменение структуры без изменения поведения |
| `test/` | тесты |
| `perf/` | производительность |
| `build/` | сборка или зависимости |
| `ci/` | CI/CD |
| `style/` | форматирование без изменения логики |
| `chore/` | прочие технические изменения |

## 4. Правила Comunicore

| Область | Что делать |
| --- | --- |
| API | сначала изменить `config/comunicore-api.yaml`, затем перегенерировать backend и frontend |
| Кодогенерация | не редактировать вручную код ogen, Hey API и sqlc |
| База данных | создать новую миграцию и выполнить `sqlc generate` |
| Backend | соблюдать направление `Handler → Service → Repository` |
| Frontend | соблюдать слои `app → widgets → features → entities → shared` |
| Состояние | TanStack Query — server state, Zustand — client state |
| Документация | обновлять вместе с поведением, API или конфигурацией |

### При изменении API

1. Измените `config/comunicore-api.yaml`.
2. Перегенерируйте ogen и frontend-клиент.
3. Запустите проверки и тесты.
4. Добавьте контракт и сгенерированный код в один PR.

### При изменении базы данных

1. Создайте новую миграцию.
2. Не изменяйте уже применённые production-миграции.
3. Обновите SQL-запросы.
4. Выполните `sqlc generate`.
5. Опишите миграцию в PR.

### Границы frontend

- импортируйте slices через public API (`index.ts`);
- не создавайте cross-slice зависимости;
- не описывайте вручную типы, сгенерированные из OpenAPI.

## 5. Проверка и Pull Request

### Backend

```bash
cd backend
go test ./...
```

### Frontend

```bash
cd frontend
npm run lint
npm run build
```

### Чек-лист перед PR

- [ ] PR решает одну задачу
- [ ] `git diff` проверен, временный код удалён
- [ ] проект собирается, тесты проходят
- [ ] сгенерированный код актуален
- [ ] миграции добавлены при изменении БД
- [ ] документация обновлена
- [ ] секреты и локальные конфиги не добавлены
- [ ] несовместимые изменения явно описаны

### Что написать в PR

- **Что:** какие изменения внесены.
- **Зачем:** какую проблему они решают.
- **Проверка:** как проверить результат и какие тесты запущены.
- **Важно:** есть ли миграции, изменения OpenAPI или несовместимые изменения.
- **UI:** приложить скриншот для изменений интерфейса.

## 6. Слияние

| Способ | Когда использовать |
| --- | --- |
| **Squash and merge** | основной вариант для обычного PR |
| **Rebase and merge** | если нужно сохранить отдельные коммиты |
| **Create a merge commit** | не использовать для обычных feature-веток |

После слияния удалите ветку.

---

## 7. Безопасность

Не добавляйте в Git:

- `.env` и конфиги с секретами;
- пароли, токены, cookie и ключи;
- приватные сертификаты;
- дампы production-базы;
- персональные данные пользователей.

Если секрет попал в commit, немедленно отзовите или замените его. Простого удаления файла недостаточно.
